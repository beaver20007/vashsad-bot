# Аудит доступа к /slots и управлению записью (handlers/booking.py)

Дата: 2026-10-03. Read-only анализ кода на `origin/main` (`1b82525`, PR #53–#55
смёржены). Изменений кода и прав доступа в рамках этого аудита **не вносилось** —
только чтение исходников. Прод-БД не запрашивалась (аудит — про архитектуру
авторизации в коде, не про текущее содержимое таблиц; реальные значения
`admin_users`/переменных окружения не читались и здесь не приводятся).

Id пользователей, где упоминаются, замаскированы или даны текстовой меткой
роли (без единой цифры), по правилу docs/ORCHESTRATOR.md от 27.09.2026.

## TL;DR

В боте **два независимых, никак не связанных друг с другом** механизма
авторизации для «сотрудника»:

1. **`admin_users` (таблица в БД)** — доступ к отдельному админ-боту
   (`admin_bot.py`, свой токен, команды `/stats /orders /broadcast /ban` и
   т.д.). Роли `owner`/`team`. Управляется изнутри бота (`/add_admin`).
2. **`DESIGNER_TELEGRAM_ID` / `DESIGNER_TELEGRAM_ID_2` / `BOOKING_RECIPIENT_IDS`
   (переменные окружения Railway)** — доступ к `/slots`, `/booking_admin` и
   всем `badm_*`-кнопкам в **основном** клиентском боте (`handlers/booking.py`).
   Управляется только сменой переменных окружения + редеплоем.

Это не ошибка кода как такового (обе проверки реализованы корректно и
применяются последовательно — см. ниже), но это два независимых списка
«кто сотрудник», которые ничем не синхронизированы. Человек, добавленный в
один список, не появляется автоматически в другом.

## 1. Кто сейчас может открыть `/slots`

Хендлер (`handlers/booking.py`):

```python
@router.message(Command("slots"))
async def cmd_slots(message: Message):
    if not _is_booking_staff(message.from_user.id):
        return
    ...
```

`_is_booking_staff(telegram_id)` → `telegram_id in _booking_staff_ids()`:

```python
def _booking_staff_ids() -> set[int]:
    ids = set(BOOKING_RECIPIENT_IDS)
    if DESIGNER_TELEGRAM_ID:
        ids.add(DESIGNER_TELEGRAM_ID)
    if DESIGNER_TELEGRAM_ID_2:
        ids.add(DESIGNER_TELEGRAM_ID_2)
    return ids
```

Итоговое множество «сотрудников записи» = `DESIGNER_TELEGRAM_ID` (если не 0)
∪ `DESIGNER_TELEGRAM_ID_2` (если не 0) ∪ **все** id из `BOOKING_RECIPIENT_IDS`
(без исключений, даже если список пуст — тогда просто не добавляет ничего).

Источник значений — три переменные окружения Railway (`config.py`, читаются
через `int(os.getenv(...))` / `_int_list_env(...)` при старте процесса).
**Не БД, не admin_users, не что-либо управляемое изнутри бота.**

## 2. Где ещё проверяется `_is_booking_staff`

Проверка (идентичная одна строка `if not _is_booking_staff(...)`) повторена
вручную в **каждом** из следующих хендлеров `handlers/booking.py` — общего
декоратора/middleware с default-deny нет, это 15 независимых copy-paste
проверок:

| Команда/callback_data                    | Назначение                              |
|-------------------------------------------|------------------------------------------|
| `/slots`, `/booking_admin`                | открыть экран управления записью         |
| `menu:booking_admin`                      | то же из инлайн-кнопки главного меню     |
| `slots:add_week`                          | автогенерация слотов на неделю           |
| `slots:list`                              | список ближайших 14 слотов               |
| `badm_addslot`, `badm_addslot_day:*`, `badm_addslot_time:*` | точечное добавление слота |
| `badm_close_list`, `badm_close_day:*`, `badm_close:*`       | закрытие слота             |
| `badm_bookings`                           | список ближайших записей                 |
| `badm_cancel:*`                           | отмена записи сотрудником                |
| `badm_resched:*`, `badm_rday:*`, `badm_resched_pick:*`      | перенос записи              |
| `badm_phone:*`                            | показать телефон клиента (алертом)       |

Проверено построчно (grep по `_is_booking_staff` и по всем декораторам,
содержащим `badm_`/`slots:`/`booking_admin`) — **пропущенных хендлеров без
проверки не найдено**. Везде поведение единообразно: для callback —
`callback.answer("Нет доступа", show_alert=True)`; для команды `/slots` —
молчаливый `return` (команда не подтверждает даже свою существование
посторонним — осознанный выбор или совпадение, из кода не видно явного
комментария об этом).

## 3. UI-слой (видимость кнопки) — не единственная защита, и это правильно

`handlers/start.py::mini_app_keyboard(telegram_id)` показывает кнопку
«⚙️ Управление записью» только когда `_is_booking_staff(telegram_id)` истинно:

```python
if telegram_id is not None:
    from handlers.booking import _is_booking_staff
    if _is_booking_staff(telegram_id):
        builder.row(InlineKeyboardButton(text="⚙️ Управление записью", callback_data="menu:booking_admin"))
```

Это **не** граница безопасности сама по себе — скрытая кнопка не мешает
прямому вызову Bot API с тем же `callback_data` (например, через сторонний
клиент/скрипт, отправляющий `callback_query` с произвольным `data`). Граница
безопасности — именно повторные проверки внутри каждого хендлера (раздел 2).
Устройство корректное (скрытие кнопки + серверная проверка — "defense in
depth"), а не "только скрытие кнопки".

Проверена также мёртвая функция `keyboards.py::main_menu_keyboard()` (ноль
вызывающих — зафиксировано в её же докстринге как заметка с трека
`booking-buttons`): кнопки «⚙️ Управление записью» там нет, только
клиентская «📅 Записаться на консультацию» (ведёт на `menu:book`, не
админ-поверхность). Непротектированной админ-кнопки в мёртвом коде нет.

## 4. `_booking_recipient_ids()` — смежная, но другая функция

```python
def _booking_recipient_ids() -> list[int]:
    if BOOKING_RECIPIENT_IDS:
        return list(BOOKING_RECIPIENT_IDS)
    return [d for d in (DESIGNER_TELEGRAM_ID, DESIGNER_TELEGRAM_ID_2) if d]
```

Используется только для рассылки уведомлений («Новая запись!», «Заявка»,
отмена/перенос) — **не для авторизации действий**. Поведение отличается от
`_booking_staff_ids()` при непустом `BOOKING_RECIPIENT_IDS`: авторизация
(`_booking_staff_ids`) добавляет `BOOKING_RECIPIENT_IDS` к дизайнерам
(объединение), а уведомления (`_booking_recipient_ids`) **заменяют** список
дизайнеров списком `BOOKING_RECIPIENT_IDS`, если он не пуст (не объединяют).
Разное поведение одной и той же переменной в двух местах — не баг (у каждой
функции есть докстринг, объясняющий разницу), но легко перепутать при
будущих правках; стоит иметь в виду.

**Риск конфигурации**: `BOOKING_RECIPIENT_IDS` — одна переменная для ДВУХ
разных целей (кто получает уведомления И кто получает права управления
записью). Если туда добавят id человека, которому нужны только уведомления
(например, администратора CRM без права управлять слотами), он автоматически
получит и доступ к `/slots`/`badm_*`. Разделения «получатель уведомлений» и
«сотрудник с правами записи» в конфиге сейчас нет.

## 5. Как это соотносится с `admin_users` / вторым ботом

`admin_bot.py` (отдельный процесс, отдельный токен, Railway-сервис
`overflowing-integrity`) использует **только** `services/admin_auth.py`:

```python
async def is_admin(telegram_id: int) -> bool:
    ...
    row = await conn.fetchrow("SELECT 1 FROM admin_users WHERE telegram_id=$1", telegram_id)
    return row is not None
```

- Таблица БД, роли `owner` / `team`.
- Bootstrap: первый `/start` в админ-бот от **пустой** таблицы автоматически
  становится `owner` (`handlers/admin_bot_handlers.py`, `admin_table_empty()` 
  → `add_admin(uid, name, "owner")`).
- Только `owner` может `/add_admin` (эскалации прав `team` → `owner` изнутри
  нет — проверено, `cmd_add_admin` требует `is_owner`).
- Команды: `/stats`, `/orders`, `/broadcast`, `/ban`, `/unban`, `/whitelist`,
  `/bans`, `/reset_onboarding`, `/add_admin` и другие (не перечисляю все —
  вне темы этого аудита, который про `/slots`).

**Между `admin_users` и `DESIGNER_TELEGRAM_ID*`/`BOOKING_RECIPIENT_IDS` нет
никакой связи в коде** — ни один файл не читает оба источника одновременно,
ни один из admin_bot-хендлеров не упоминает booking/slot. Это подтверждено
grep по `handlers/admin_bot_handlers.py` на `booking|slot` — совпадений нет.

Практическое следствие: пригласить нового человека в управление записью
(`/slots` в основном боте) и дать ему доступ к `/stats`/`/orders` в
админ-боте — **две совершенно раздельные операции** с разными механизмами
(смена переменной Railway + редеплой vs. `/add_admin` внутри чата). Ничто в
коде не напоминает сделать второе при первом и наоборот.

## 6. Мелкие наблюдения (не критично, не в рамках исправления)

- **Bootstrap-гонка `admin_users`**: `admin_table_empty()` (SELECT) и
  последующий `add_admin()` (INSERT) в `cmd_start` админ-бота не атомарны
  одной транзакцией — если два разных человека отправят `/start` в
  пустую-ещё таблицу практически одновременно, оба теоретически могут
  пройти проверку "таблица пуста" и оба стать `owner`. Вероятность на
  практике низкая (токен админ-бота знает узкий круг людей, временное окно
  — только сразу после первого деплоя/сброса БД), но механически это гонка,
  не "проверить и записать одной операцией".
- **`/export_csv` читает `DESIGNER_TELEGRAM_ID` напрямую из `os.getenv(...)`**
  (`handlers/export.py`, минуя уже распарсенную константу `config.py`) —
  практически то же значение, но отдельный путь чтения, не унифицированный
  с остальными проверками в том же файле (`/export`, `/export_clients` берут
  константу из `config`). Несогласованность стиля, не брешь.
- **`/slots` молчит для посторонних, callback-и отвечают "Нет доступа"** —
  разное поведение для команды и для кнопок при одинаковой логике допуска;
  возможно, осознанно (не подтверждать существование команды), возможно —
  просто так сложилось по ходу разработки разными треками. Не менял ничего
  по этому пункту — фиксирую для Beaver.
- Отдельного **аудита/лога** вида «кто и когда закрыл слот Х» нет — только
  `log.warning`/`log.error` при ошибках, успешные действия сотрудников в лог
  не идут. Не проблема прав доступа как таковая, но при расследовании спора
  между Beaver/Аней «кто закрыл этот слот» ответа в логах сегодня нет.

- Содержимое таблиц `admin_users`/переменных `DESIGNER_TELEGRAM_ID*`/

  Beaver не вносить").

## Не проверено / ограничения этого аудита

- Реальное поведение Telegram Bot API при попытке отправить `callback_query`
  с произвольным `callback_data` от бота/скрипта не владельца аккаунта —
  не воспроизводил живьём (теоретический довод в разделе 3 основан на
  документации Bot API, не на эксперименте).
- Не проверялось, есть ли в `vashsad-miniapp` (другой репозиторий) свой
  параллельный механизм доступа к управлению записью/слотами, который мог
  бы дублировать или конфликтовать с описанным здесь — миниапп прямо вне
  рамок брифа.
- Git-история причин, почему выбраны именно env-переменные для
  booking-staff (а не таблица, как для `admin_users`) — не исследовалась;
  описано только текущее состояние кода, не "почему так вышло".
