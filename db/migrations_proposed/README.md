# db/migrations_proposed/ — не применяется этим репо

Этот бот (`vashsad-full`) не имеет собственного раннера миграций —
только идемпотентные `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ADD
COLUMN IF NOT EXISTS` в `services/database.py`, выполняемые при
старте. Настоящий раннер (`db/migrate.py`, таблица `schema_migrations`,
нумерация 000-016) живёт в `vashsad-miniapp`, потому что там же —
единственная общая БД (Neon), которую бот делит с miniapp.

Файлы в этой папке — **дизайн, не применённая миграция**:
- SQL проверен только глазами и `psql --dry-run`-стилем (синтаксис),
  **не прогонялся на реальной БД**.
- Не пронумерован в последовательности miniapp (000-016) — при
  реальном накате его нужно скопировать в
  `vashsad-miniapp/db/migrations/017_content_texts_{up,down}.sql`
  (следующий свободный номер на момент написания) и прогнать через
  `db/migrate.py apply` **из репозитория miniapp**, координируя с тем,
  кто ведёт эту сессию — это чужой репозиторий, трогать его файлы
  отсюда не в мандате этого трека (см. Track 7 в отчёте по этой же
  причине).
- Данные в seed-секции up-миграции — **буквальная копия текущего
  текста бота** (включая спорное «дипломированный ландшафтный
  дизайнер» — см. `docs/ORCHESTRATOR.md` про несостыковку с miniapp).
  Формулировку должна утвердить Аня перед реальным накатом — эта
  миграция сознательно не решает содержательный вопрос, только
  переносит место хранения.

## Применение (когда владелец даст ход)
1. Бэкап БД (см. `CLAUDE.md` владельца — "перед DDL — бэкап, даже
   ритуальный").
2. Скопировать `content_texts_up.sql`/`content_texts_down.sql` в
   `vashsad-miniapp/db/migrations/` под следующим свободным номером.
3. `python db/migrate.py apply --dry-run` → проверить план.
4. `python db/migrate.py apply --yes` (из `vashsad-miniapp`, через
   `DATABASE_URL_UNPOOLED`).
5. Только после этого — трек 5 (переключение чтения текстов в боте на
   эту таблицу) становится безопасным для реального деплоя.
