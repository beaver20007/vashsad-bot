# db/migrations_proposed/ — не применяется этим репо

Этот бот (`vashsad-full`) не имеет собственного раннера миграций —
только идемпотентные `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ADD
COLUMN IF NOT EXISTS` в `services/database.py`, выполняемые при
старте. Настоящий раннер (`db/migrate.py`, таблица `schema_migrations`,
нумерация 000-020) живёт в `vashsad-miniapp`, потому что там же —
единственная общая БД (Neon), которую бот делит с miniapp.

## Схема сверена с vashsad-miniapp (09.09.2026-10)

`vashsad-miniapp` параллельно спроектировала ту же таблицу в своём
PR #120 (`db/migrations/020_content_strings_{up,down}.sql`) под тем же
ночным брифингом. Изначально здесь была своя версия под именем
`content_texts` (flat key + TEXT) — **переписана** под схему miniapp
(`content_strings`, `namespace`+`key`+`value JSONB`), см. подробности
и список отличий в комментарии наверху `content_strings_up.sql`.

Файлы в этой папке — **дизайн, не применённая миграция**:
- SQL проверен только глазами (синтаксис + сверка построчно со схемой
  `020_content_strings_up.sql` в PR miniapp), **не прогонялся на
  реальной БД**.
- Не пронумерован в последовательности miniapp — при реальном накате
  логичнее применить **только `020` из miniapp** (там уже есть
  номерной слот в их раннере) и не создавать вторую CREATE TABLE
  отсюда же — эти файлы держим как зеркало/документацию решения со
  стороны бота, а не как отдельный второй накат той же таблицы.
  Если решат накатывать всё же отсюда — сначала подтвердить, что 020
  в miniapp НЕ применена и не будет применена параллельно (иначе
  вторая CREATE TABLE упадёт на дублирующей таблице).
- `designer_bio.default` — окончательные значения (решение владельца
  09.09.2026), совпадают с черновиком miniapp буквально: тот черновик
  владелец и утвердил как финальный.
- `order_status.*` — **НЕ засеяно здесь, конфликт с `020` не решён**:
  у бота и miniapp разные тексты для одних и тех же
  `(namespace, key)` (пример и детали — в комментарии
  `content_strings_up.sql` перед местом, где был бы INSERT).
  Нерешено, требует отдельного решения владельца по каждому статусу.

## Применение (когда владелец даст ход)
1. Бэкап БД (см. `CLAUDE.md` владельца — "перед DDL — бэкап, даже
   ритуальный").
2. Согласовать с владельцем: накатывать `020` из `vashsad-miniapp`
   (рекомендуется, там уже settled `designer_bio`) или эти файлы —
   не оба.
3. Прежде чем накатывать — решить `order_status.*` (см. выше), иначе
   таблица останется без текстов статуса и оба бота продолжат читать
   свои старые хардкоды через fallback (не крашится, но толку от
   миграции без этого шага меньше).
4. `python db/migrate.py apply --dry-run` → проверить план (из
   `vashsad-miniapp`, `DATABASE_URL_UNPOOLED`).
5. `python db/migrate.py apply --yes`.
6. Только после этого — трек `feat/t-content-texts-reads` (PR #32,
   переключение чтения текста дизайнера в боте на эту таблицу)
   становится осмысленным на реальной БД (код там уже безопасен и без
   миграции — просто продолжит идти на fallback).
